# 日志展示与字段精简实施方案

日期：2026-11-13

状态：已实施并完成本地审查与自动化验证；真实 DM 场景待环境验证。实际结果、性能代价与验证边界见[实施与审查记录](日志改造实施与审查记录.md)。本文保留方案定义及验收要求。

## 1. 问题与目标

当前问题是单条日志的信息密度低、重点不突出。用户主要关注 INFO 的显示，同时希望 DEBUG 保持可排查性。

根据提供的日志，SQL 开始与结束各携带约 27 个字段，SQL 错误约 33 个字段，整轮结束约 22 个字段。根因是不同事件共用完整状态快照：正常值、尚未产生的结果、内部诊断管理状态和实际故障证据混合输出。控制台还直接展示 JSON 字段及通用日志调用位置。

目标：

- INFO 能快速看出启动状态、采集耗时、产出和异常数量。
- ERROR/WARN 能直接定位数据源、采集器、失败原因，并追查完整证据。
- DEBUG 能按关联编号还原过程，开始、完成、阶段、异常分别选择字段。
- 控制台采用中文摘要；文件采用精简的结构化 JSON，保留稳定英文事件名。
- 保留 SQL 原文、原始错误、必要计时和前台/后台归属，明确各种计数与时间的含义。

本次交付包含日志字段、显示、启动输出和配套文档。采集 SQL、指标及标签、查询执行顺序、缓存行为、超时预算、Top 排名与触发条件作为回归约束。

## 2. 已确定的方案

| 项目 | 决定 |
|---|---|
| 控制台格式 | 时间、级别、中文事件、固定顺序的关键项，以竖线分隔 |
| 文件格式 | 一条逻辑事件一行 JSON；保留 `ts/level/msg/caller` |
| 日志级别 | 沿用 debug/info/warn/error；本次不修改用户现有 logLevel |
| 正常 INFO | 每轮一条采集完成摘要 |
| 异常 | 独立错误/警告，加整轮摘要中的异常计数 |
| SQL 全文 | 错误、兼容探测错误、慢 SQL 排名保留；DEBUG 文件在 SQL 开始时保留一次 |
| 详细 SQL 的控制台显示 | 同一个事件渲染成摘要行和 SQL 详情行，级别相同 |
| 普通成功 SQL 的控制台显示 | DEBUG 显示开始和完成摘要，不展开全文 |
| 关联编号 | 文件保留完整 scrape_id/run_id/query_id；控制台使用派生短号 |
| 开关 | 使用现有级别和 scrapeSlowThresholdMs，避免增加显示选项组合 |

“摘要行＋详情行”是控制台对同一事件的显示方式。业务代码只发出一次事件，JSON 文件只写一次，不额外创建 sql_detail 事件。这让 SQL 错误在 INFO/WARN/ERROR 配置下仍能查到原文，同时避免文件重复写入。

## 3. 最终显示示例

以下 S1 代指实际轮次的控制台短号。正常 SQL 与错误取自用户日志；慢采集、缓存和超时场景是格式示例。

### 3.1 启动

```text
2026-11-13 10:06:49.567  INFO   启动服务 | dameng_exporter v1.2.7_20261109
2026-11-13 10:06:49.567  INFO   加载配置 | 启用数据源 1 | 采集模式 blocking | 慢采集阈值 30s
2026-11-13 10:06:49.567  INFO   数据源就绪 | 数据源 prod_primary_01 | 节点类型 DEFAULT
2026-11-13 10:06:49.567  INFO   自定义指标加载完成 | 数据源 prod_primary_01 | 定义数 5
2026-11-13 10:06:49.567  INFO   注册完成 | 采集器 36
2026-11-13 10:06:49.567  INFO   启动监听 | 指标地址 http://localhost:9200/metrics
```

启动监听记录保留完整指标访问地址，方便直接打开；仅端口或通配地址转换为 localhost，明确配置的主机或 IP 按原值组成 URL。文件同时保留 address、metric_path 和 url。现有程序在 ListenAndServe 前输出日志，此处不提前宣称监听已成功。监听失败仍独立输出 ERROR。

完整配置按字段进入 DEBUG；常规启动不打印多行配置框、项目地址或重复的初始化数量。配置成功信息在 logger 初始化后统一记录；初始化前配置加载失败仍通过 stderr 报错并退出。

节点探测信息与连接池建立信息合并到数据源就绪事件。禁用的数据源进入 DEBUG；连接失败、探测失败和恢复状态继续独立记录。自定义指标保留每个数据源的一条加载结果，重复的总量说明进入 DEBUG。

### 3.2 正常采集

```text
2026-11-13 10:07:19.499  INFO   采集完成 | 耗时 55ms | 采集任务 36 | SQL 55 | 样本 135 | 关联 S1
```

`runs` 是运行次数，可能包含同一采集器在不同数据源上的执行，因此显示“采集任务”。`samples` 是指标样本数，因此显示“样本”；不把它解释为指标种类数。启动时的“采集器”是实际注册数，口径不同。

同一事件的文件记录如下，普通完成仅需核心字段：

```json
{"ts":"2026-11-13T10:07:19.499+08:00","level":"INFO","caller":"diagnostics/trace.go:445","msg":"scrape_finished","scrape_id":"20261113T020649.558007000-1","collection_duration_ms":55,"runs":36,"sql_calls":55,"samples":135}
```

caller 行号仅为当前源码位置示例，实施后由 zap 自动记录实际调用位置。

### 3.3 SQL 失败

```text
2026-11-13 10:07:19.470  ERROR  SQL执行失败 | 数据源 prod_primary_01 | 采集器 DbJobRunningInfo | 阶段 查询 | API耗时 25ms | 原因 "Error -2103: 第14 行附近出现错误:\n无效的模式名[SYSJOB]" | 关联 S1/R28/Q6
2026-11-13 10:07:19.470  ERROR  SQL详情 | 关联 S1/R28/Q6 | SQL "<原始 SQL 全文>"
2026-11-13 10:07:19.499  INFO   采集完成 | 耗时 55ms | 采集任务 36 | SQL 55 | 样本 135 | 异常任务 1 | SQL失败 1 | 关联 S1
```

示例中的 SQL 占位符在实际运行时替换为未经截断的原文。原始错误只在主行输出一次；错误码和驱动行号不通过正则强行拆分，不推断数据库功能应如何启用。

异常任务数和失败 SQL 数分别表示运行次数与应用 SQL 调用次数，两者可能重叠，不能相加。整轮事件叫“采集完成”，不把出现一条 SQL 错误描述成所有采集任务失败。

### 3.4 前台超时及后台结束

```text
2026-11-13 10:07:24.444  WARN   采集前台超时 | 数据源 prod_primary_01 | 采集器 TableSpaceDateFileInfo | 前台预算 5s | 后台结束待确认 | 关联 S2/R2
2026-11-13 10:07:24.450  INFO   采集完成 | 耗时 5.006s | 采集任务 36 | SQL 55 | 样本 120 | 异常任务 1 | 前台超时 1 | 关联 S2
2026-11-13 10:07:27.444  INFO   采集后台结束 | 数据源 prod_primary_01 | 采集器 TableSpaceDateFileInfo | 启动后历时 8s | 后台SQL 1 | 关联 S2/R2
```

新增独立 collector_timeout 警告：当前 Detach 主要记录计数和触发信息，阈值未到时不能依靠慢采集诊断提示前台超时。每个 run 首次成功 Detach 后输出一次警告，不额外调用数据库或改变等待、取消与转发行为。

background_duration_ms 当前从 run 启动时计算，因此中文使用“启动后历时”，不误称“转后台后耗时”。后台阶段保留 phase=background，不回写已完成轮次的计数。

### 3.5 慢采集

```text
2026-11-13 10:07:49.444  INFO   采集耗时达到阈值 | 已耗时 30s | 阈值 30s | 未完成任务 2 | 活跃SQL 1 | 关联 S3/P1
2026-11-13 10:07:49.444  INFO   SQL耗时排名 #1 | 数据源 prod_primary_01 | 采集器 TableSpaceDateFileInfo | API耗时 28s | 总历时 30s | 状态 执行中 | 阶段 读取下一行 | 启动时剩余预算 35s | 关联 S3/R2/Q1/P1
2026-11-13 10:07:49.444  INFO   SQL详情 | 关联 S3/R2/Q1/P1 | SQL "<原始 SQL 全文>"
```

S 表示轮次、R 表示采集运行、Q 表示 SQL 调用、P 表示快照。慢采集总览有活动阶段时追加阶段摘要；存在“读取未确认、前台已截止、启动时 context 已失效”等状态时明确显示。

### 3.6 DEBUG

```text
2026-11-13 10:07:19.444  DEBUG  SQL开始 | 数据源 prod_primary_01 | 采集器 TableSpaceDateFileInfo | 启动时剩余预算 4999ms | 关联 S1/R2/Q1
2026-11-13 10:07:19.446  DEBUG  SQL完成 | 结果 成功 | API耗时 1ms | 读取 5行 | 关联 S1/R2/Q1
2026-11-13 10:07:19.446  DEBUG  采集器完成 | 数据源 prod_primary_01 | 采集器 TableSpaceDateFileInfo | 耗时 2ms | SQL 1 | 样本 20 | 关联 S1/R2
```

最后一行的采集器产出数仅用于展示格式。query_name/query_index 在调用点已声明时展示；未声明时使用 collector 和 query_id，不新增需要维护的全局 SQL 名称映射表。

普通 SQL 完成时，文件仍带数据源、采集器和完整关联字段以便独立检索；控制台完成行通过关联编号连接开始行。错误与慢 SQL 主行始终带数据源和采集器。

## 4. 字段规则

### 4.1 通用规则

1. 每种事件分别构造字段，不再共用 fields(full bool) 输出全部状态。
2. 文件使用稳定的英文 msg 和字段名；中文文案只存在于控制台展示层。
3. 核心计数即使为零也输出，例如 samples=0、sql_calls=0、rows_read=0。
4. 被定义为可选的异常计数省略表示零；可选布尔标志省略表示 false。该约定只适用于字段表声明的键，不做全局“删除所有零值”。
5. rows_read=null 表示未知，不能转换成零。预算 null 表示没有 deadline，0 表示预算耗尽，两者均须准确表达。
6. 正常 phase=collection 可以省略；所有后台事件必须明确携带 phase=background。业务领域 scope=exporter 有实际区分作用时保留。
7. event 自身已经表达的开始、完成状态不重复输出。Top 是过程快照，仍保留独立 state/result/sql_phase，避免混淆生命周期和执行结果。
8. 关联字段和数据源等名称保持原值；控制台按既定规则转义用户字符串中的换行、制表符、引号、竖线及控制字符，避免伪造日志结构。

### 4.2 事件字段表

所有 SQL 文件事件均带 scrape_id/run_id/query_id/datasource/collector。所有 run 事件带 scrape_id/run_id/collector，数据库 run 带 datasource；省略空 datasource。

| 事件 | 常驻字段（关联字段之外） | 按条件补充 |
|---|---|---|
| scrape_started / DEBUG | scrape_id | 无需重复 phase=collection |
| scrape_finished / INFO | scrape_id、collection_duration_ms、runs、sql_calls、samples | 非零异常/跳过计数；已发布的 snapshot_id；本次实际发布排名时的 top_emitted_count |
| scrape_diagnostic / INFO | scrape_id、snapshot_id、collection_duration_ms、threshold_ms、runs_active、sql_active、trigger | active_stages 非空；本次 top_emitted_count；已发生的异常计数 |
| collector_started / DEBUG | 运行关联字段 | fast 模式及 worker 预算；exporter 范围标识 |
| collector_finished / DEBUG | duration_ms、sql_calls、samples | skipped/detached 状态；skip_reason；issue=true；非零失败/丢弃；实际缓存来源及回退；前台截止时间 |
| collector_stage_started/finished / DEBUG | flow、stage | background 标记；阶段记录保持原有开始/结束时机 |
| collector_error / ERROR | reason、原始 error | background 标记及相关业务上下文 |
| collector_panic / ERROR | panic、完整 stack | background 标记 |
| collector_timeout / WARN | mode=fast、timeout_ms、timeout_scope=worker、foreground_cutoff_at | 只在首次 Detach 时输出 |
| collector_background_finished / INFO | phase=background、background_duration_ms、background_sql_calls | 非零 background_sql_error_calls |
| sql_started / DEBUG | 启动时预算、sql 原文 | 已声明 query_name/query_index/purpose；非 active 的 context_state_at_start；background |
| sql_finished / DEBUG | result、sql_duration_ms、rows_read、read_scope | 读取不完整状态；sql_wall_ms 与 API 累计耗时的毫秒值不同；API 耗时分项；首次错误阶段及实际重复次数 |
| sql_error / ERROR | error、error_stage、sql_duration_ms、启动时预算、sql 原文 | 非正常 context、实际 timeout/context_expired、不同的 error_stage_observed、可观察读取结果；超时场景的 API 分项和总历时 |
| sql_probe_expected / DEBUG | 兼容探测原始错误、error_stage、启动时预算、sql 原文 | 已声明的 purpose 等元数据；适用规则同 sql_error |
| sql_top / INFO | snapshot_id、rank、state、result、sql_phase、sql_duration_ms、sql_wall_ms、启动时预算、sql 原文 | 读取异常、错误阶段、context 异常、background、自定义查询元数据及 API 分项 |

文件中的普通 DEBUG sql_started 保留一次完整 SQL，用于排查成功查询历史；sql_finished 不再复制全文。控制台普通 sql_started 不展开全文。INFO 未记录的成功 SQL 历史不能在事后切换 DEBUG 后补回。

sql_finished 的正常读取省略 read_state=complete，但保留 read_scope，避免把“已读第一行/第一个结果集”解释为“所有结果集已消费”。读取异常时保留 partial/unconfirmed/not_started。SQL 错误记录若读取结果尚未确定，按观察事实输出，不宣称已完成；首次错误阶段保留。

### 4.3 明确删除及调整

| 字段 | 调整 |
|---|---|
| query_sequence | 从日志删除；内部序号继续用于排序及 query_id 生成 |
| sql_started 的 state/result/read_state/rows_read/各种耗时 | 删除；开始时尚无结果 |
| sql_finished 的 state=finished、sql_phase=done | 删除；事件名已表达 |
| error_repeat_count=0 | 从错误事件删除；完成时有实际重复才输出重复计数 |
| error_stage_observed | 仅与首次 error_stage 不同时输出 |
| skipped=false、cache_fallback=false、issue=false | 省略；skipped 用 run_state=skipped 表达 |
| mode=blocking/direct、timeout_scope=none、timeout_ms=0 | 不在每条上下文中重复；配置摘要及必要的运行开始记录解释模式 |
| forwarding_finished_at | 普通完成记录用事件时间；只在截止/转发边界需要解释时补充 |
| snapshot_at | 慢诊断保留快照采样时间，普通完成摘要省略 |
| threshold_ms | 进入慢诊断时展示；正常完成摘要省略 |
| diagnostic_reasons | 从普通完成摘要删除；具体异常由独立事件及计数表达，慢诊断保留 trigger |
| top_count/top_refreshed/last_top_snapshot_id | 替换为明确的 snapshot_id 与 top_emitted_count；无诊断不携带 |
| 八个平铺 API 耗时 | 改为诊断/DEBUG 完成记录中的 api_ms 对象，按观测及适用性构造 |

api_ms 对象采用 query/next/scan/err/close/columns/column_types/row_scan 键。省略的分项表示未观测或不适用；实际发生但不足 1ms 的调用可以记为 0。QueryRow.Scan 内部不可拆分的阶段继续按 row_scan 记录。普通错误没有超时/context 异常时，不强制附性能分项。

summary 中 snapshot_id 表示本轮最后已发布的排名快照；top_emitted_count 表示紧随本事件实际打印的排名数量，未打印时省略。诊断总览和最终摘要使用同一解释，无 SQL 的慢轮次仍可有快照编号，但不制造排名。

字段输出变化要求更新日志消费者。文件原有事件名和保留字段的含义维持稳定；上述删除项和新键的迁移说明随版本一起发布。

## 5. 控制台展示规则

- 固定顺序：时间、级别、事件、定位信息、结果/耗时、异常、关联。
- 时间格式使用本机时间 `YYYY-MM-DD HH:mm:ss.SSS`；文件继续 ISO8601 毫秒时间及偏移。
- 耗时不足 1 秒使用 ms，达到 1 秒使用最多三位小数的 s，去掉末尾零。文件始终使用原有整数毫秒，显示 0ms 可能是毫秒取整。
- INFO/WARN/ERROR 主行省略通用日志调用位置；文件保留 caller，DEBUG 可在末尾显示 caller。
- 普通事件一条主行。SQL 错误、预期探测错误和 sql_top 有 SQL 时增加同级详情行；panic 的完整栈作为同事件详情输出。
- SQL、原始错误和堆栈采用可逆转义；每条展示记录只有一个物理行。显示值包含分隔符时使用带引号的转义表示。
- 同一事件的摘要和详情先构造成一个缓冲，再在共享写锁下成组写出，避免并发事件插入两行之间。不能为日志 I/O 持有 diagnostics 状态锁。
- 未迁移的事件采用兼容展示；未知事件名或未知字段不得静默丢弃，保留原消息及附加键值。明确列入精简规则的键除外。
- 控制台短号从完整 scrape_id 的现有递增后缀派生，无需维护编号映射。无法识别的 ID 原样展示。短号用于单个进程的控制台阅读，跨进程定位使用文件完整 ID 与时间，不把 S1 当成全局唯一键。
- 不通过颜色表达唯一信息；关闭颜色或重定向后仍可读。

## 6. 代码实施设计

### 6.1 输出链路

```text
诊断/启动/数据源事件
        ↓
按事件构造精简字段
        ↓
zap tee
  ├─ 文件 core → 英文事件与结构化 JSON → 现有轮转文件
  └─ 控制台 core → 中文模板 → 主行与必要详情 → stdout
```

在 logger 新增事件感知的 console core，保留现有文件 core。Core.With 保存不可变上下文，Check/Enabled 遵循当前级别，Write 合并上下文与事件字段后渲染；派生 core 共用同一个带锁输出目标。直接处理 zap 字段，避免先编码 JSON 再解析。

console core 不额外发 logger 事件，避免递归输出、重复文件记录与重复计数。Write 合并同名上下文时采用事件字段优先；调用点同步清理重复 With，文件也应避免同名键。未知结构仍通过 zap 编码器安全输出。

### 6.2 诊断数据与日志字段分离

- querySnapshot、counts、阶段状态仍保存诊断所需原始数据。
- 给 API 分项增加固定大小的已观测位图，区分“执行过但耗时取整为零”和“未观测”；位图和计时值在同一状态锁下更新，不增加逐调用历史缓存。
- 用 startedFields/finishedFields/errorFields/topFields 等有明确用途的构造方法替换 fields(full bool)。
- 将 round snapshot 的统计数据与 fields 数组分开；Finish 根据结构化计数判断异常，不再遍历字段数组查 issue_runs。
- 移除 RunTrace.finish 中依赖字段位置的 `f[5] = "collection"`，显式构造前台完成上下文。
- RunTrace.Fields 对业务日志只提供关联上下文；fast 预算和模式由需要它们的事件附带。
- 日志格式化和 I/O 在状态锁外执行；关闭 DEBUG 时不为 DEBUG 构造 SQL 展示和耗时分项。
- 扩充 diagnostics.Logger 的 Warnw 能力，更新 discard 与测试日志实现，为 collector_timeout 提供明确级别。
- 错误识别、ExpectedError、错误去重仍以原始 error 链和原有规则为依据，不能根据中文展示文案判断。

### 6.3 启动及业务日志

- main 使用 exporter_starting/config_loaded/server_listening/server_failed 等结构化事件。
- db 连接池建立成功事件携带数据源与已识别节点类型；节点探测耗时进入 DEBUG，避免重复 INFO。
- 修正 SugaredLogger.Info/Error/Infof 等误传 zap.Field 的调用，改用 Infow/Errorw 或 Desugar().Info/Error。用户日志中的 `{datasource 15 0 ... <nil>}` 正是此类显示问题。
- register_multi 与 custom_multi_source_adapter 输出一次明确的注册或加载结果；计数由实际注册和解析结果产生。
- 清理 collectorLog.log/newCollectionRun 中重复或过大的日志上下文，保留 datasource、collector 和关联编号。
- 将 SYSJOB 相关长提示改为简洁的能力缺失提示，关联原 SQL 错误。提示“任务指标未采集，请检查任务功能配置”，不凭一个模式错误建议直接执行初始化操作；保持原条件分支和采集降级行为。
- DB 连接错误、恢复、认证错误及其他现有 WARN/ERROR 继续可见，优先统一已知事件，其余使用兼容格式。

## 8. 验收与测试

### 8.1 功能与显示

| 场景 | 验收要求 |
|---|---|
| INFO 正常采集 | 只有一条完成摘要，固定顺序，无 JSON 字段块；0 样本/0 SQL 仍正确显示 |
| INFO 一条 SQL 错误 | 控制台一个错误主行加一个同级 SQL 详情；文件一个完整 sql_error；汇总计数正确 |
| WARN/ERROR 级别 | 错误 SQL 原文仍可用；INFO 摘要按现有级别规则被过滤 |
| 非 SQL 业务错误及 panic | 原始原因可查；panic 栈完整，普通 SQL 错误不自动附栈 |
| fast 前台超时 | 每个 run 一条独立 WARN；即使未到慢采集阈值也可见；前后台计数保持隔离 |
| 慢采集与最终排名刷新 | 达到原阈值才触发；最多五条排名；候选与时长规则保持；只增长毫秒不重复刷新 |
| 预期探测失败 | 保持 DEBUG；权限、网络、未知错误不能被降为预期探测 |
| SQL 与超时预算 | 无 deadline、耗尽、启动已失效、共享预算逐步耗尽均准确表达 |
| 读取覆盖 | first_row/first_result_set、partial/unconfirmed、未知行数与零行不混淆 |
| 并发采集和后台退出 | 文件完整 ID 唯一关联；主行与详情成组写出；前台结束后日志不串入下一轮 |
| SQL/错误/栈包含特殊字符 | 文件 JSON 可逆；控制台可恢复原文；引号、换行、竖线等不破坏记录结构 |
| 数据源、配置、启动错误 | 禁用/连接失败/恢复/加载失败/监听失败信息准确，不预报成功 |
| 未知事件与 With | 上下文正确继承；未知字段有兼容输出；文件不因 renderer 重复或丢字段 |
| 输出失败 | core.Write 返回写入错误；文件与控制台 tee 的错误传播可验证 |

原有 logger 测试要求控制台尾部是可解析 JSON，这一断言按新展示格式替换。文件的 JSON 可逆性保持原有强度；控制台改验证逐值转义可逆、关联关系与成组输出。

原有 diagnostics 测试中直接索引“零值字段”的断言按字段省略规则调整，测试仍需证明对应计数/业务事实未丢失。不能通过删除超时、并发、读取、预算和排名测试来适配新格式。

### 8.2 数量与长度

- 正常 INFO 每轮仍是一个语义事件、一条控制台摘要、一条文件记录。
- 慢诊断每轮仍最多 12 个 INFO 语义事件；每个 Top 在控制台附 SQL 详情后最多 22 条展示记录。错误、后台退出、数据源状态事件另计。
- 一条 sql_error 文件记录可渲染成两条 ERROR 展示记录，不计作两个业务错误。
- 以本文固定样例作为目标：普通 INFO 采集摘要约 160 个显示字符以内；用户这轮有异常的摘要约 200 个显示字符以内。按去除 ANSI 的 Unicode 字符数统计，包含时间与关联号。
- 固定样例的文件完成摘要相对原 22 字段示例至少减少 40% 字节。该指标针对同样数据生成的记录对比，不包含 SQL 全文。
- 长数据源名、长错误和 SQL 全文允许超出示例长度，不通过截断满足指标。
- 普通 SQL 开始不输出未产生的结果/耗时；完成不复制 SQL；这些规则直接通过字段契约验收。

### 8.3 自动化检查

在同一环境保存改造前后基线，比较 ns/op、B/op、allocs/op、sql/op、日志事件数、控制台字节数与文件字节数。性能比较在关闭/开启 DEBUG 的对应级别分别执行；确定存在重复格式化、额外 SQL 调用或持续增长的历史缓存时必须修复。日志变短不直接等同于 CPU 更省。

## 9. 兼容、发布与回退

- 文件保留 JSON，普通事件保留 msg 作为检索入口。日志解析依赖旧字段时，按第 4 节迁移；省略异常计数按零处理，不能推广到未知行数和无 deadline。
- 控制台改为中文文本；依赖原控制台 JSON 的采集器应改读文件。该变化及字段删减写入发布说明。
- 完整 SQL 保留现有字面量，绑定参数和结果集继续不进入日志；启动配置展示沿用现有凭据保护。
- 控制台只对已知事件进行定制；兼容输出保证其他业务日志仍可见。
- 部署后确认一轮正常采集、一轮错误显示、日志文件解析、轮转、指标输出与原行为一致。
- 回退优先按实施阶段撤回对应提交。回退控制台不会影响文件 core；回退字段精简会恢复旧字段。无需迁移配置文件。
