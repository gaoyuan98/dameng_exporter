# 采集诊断问题修复与收敛实施方案

日期：2026-11-12。状态：待实施。本文件整理当前代码审查发现的问题及实施决策，不代表代码已修复或现场验收已完成。

本轮目标是修复数据完整性问题、控制默认日志体积、减少注册入口的共享状态。基于现有诊断实现做小范围修改，按“业务修复 → 日志收敛 → 注册清理 → 文档与验收”交付。

**1. 问题依据与交付边界**

| 事项 | 当前证据 | 本轮交付 |
| --- | --- | --- |
| 表空间、数据文件缓存不完整结果 | 模拟首轮读取中断后返回 `partial/rows_error`，次轮返回 `unknown/cache_unverified`，两轮仅执行一次 SQL | 只缓存完整读取的结果；缓存解析失败不混入残留数据 |
| 自定义查询遗漏读行错误 | 模拟返回一行后读行中断，`queryDynamicDatabase` 仍返回一行和 `error=nil` | 检查 `rows.Err()`，错误透传并进入现有关联日志路径 |
| 默认零样本名单无上限 | 每轮汇总输出全部零样本项，包括正常的无数据场景 | 完整计数、有限明细、明确省略数量，DEBUG 可恢复全量 |
| 注册列表仍使用包级变量和锁 | `collectors`、`registerMux` 仅用于注册入口；最终列表已交给 `scrapeCollector` | 改为函数局部列表，删除相应全局变量和锁 |
| 文档与变更范围需要收敛 | 原方案、验收记录与排查指南重复描述行为；工作区另有面板修正 | 使用指南维护当前行为，历史材料保留阶段语义；面板差异单独交付 |

前两项为原有业务缺陷，当前诊断改造未修复。后三项为收敛与维护性工作，不作为已证实的业务回退描述。

保留已有轮次编号、上下文日志、慢提示阈值、execution/outcome 分离、fast 前后台隔离和首批四项结果分类。其余采集器继续使用 `unknown`，本轮不全面迁移结果接口，不增加诊断指标、逐 SQL 计时、缓存版本协议或新的通用执行框架。SQL、指标名称/标签、缓存键/有效期、采集模式与超时预算沿用当前实现；以下明确列出的错误路径允许行为修正。

**3. B1：只缓存完整读取结果**

两类采集器采用相同规则，不新增共享缓存框架。

1. 缓存 JSON 解码到临时切片，只有解码完整成功才用于输出。解码失败时丢弃临时切片，以空切片开始数据库查询，设置 `cache_fallback=true` 并保留原错误日志。
2. 查询和读行仍沿用现有行为：有效行可在本轮输出；Scan 错误继续读取后续行；`rows.Err()` 优先于 Scan 错误作为最终原因。
3. 在输出当前轮有效行之后，仅当 Query 成功、所有 Scan 成功、`rows.Err()==nil` 时执行序列化和缓存更新。完整零行允许缓存；读取失败或部分读取不调用 `SetCache`。
4. 序列化失败仅记录错误，不覆盖缓存，不改变已经输出的业务结果。
5. 本轮不额外删除解析失败的共享缓存项：成功查询覆盖它，查询失败则下一轮继续回源。这样不会因一个较晚执行的失败分支误删另一并发轮次刚写入的完整缓存；本地残留数据必须清空。

缓存回退后的结果分类相应调整：

| 路径 | 本轮输出 | 结果 | 缓存动作 |
| --- | --- | --- | --- |
| 可解析的现有缓存命中 | 缓存样本 | `unknown/cache_unverified`，`data_origin=cache` | 不更新 |
| 完整查询且有有效行 | 数据库样本 | `success`，`data_origin=database` | 序列化成功后写入 |
| 完整查询且零行 | 无样本 | `empty`，`data_origin=database` | 缓存空结果 |
| Scan/读行错误且有有效行 | 仅有效行 | `partial/scan_error` 或 `partial/rows_error` | 不写入 |
| Scan/读行错误且无有效行 | 无样本 | `failed/scan_error` 或 `failed/rows_error` | 不写入 |
| 缓存解析失败后完整查询 | 仅新查询的样本 | `success` 或 `empty`，`cache_fallback=true` | 序列化成功后覆盖 |
| 缓存解析失败后查询或读行失败 | 仅按查询路径允许输出的有效行 | 对应 `failed/partial`，`cache_fallback=true` | 不写入 |

删除 `tableOutcome` 中仅因 `cacheFallback` 就判为 `cache_recovery_unverified` 的分支；保留回退标记，缓存命中继续保守记为 unknown。缓存没有完整性元数据，因此不把所有缓存命中直接改判 success。

验收必须跨轮次检查：第一轮“成功读一行后中断”不产生缓存；第二轮数据库恢复后必须再次查询并输出完整结果；第三轮才命中新缓存。再覆盖全行失败、坏缓存含部分可解析内容、坏缓存回退后再次失败及完整零行缓存。通过受控并发验证失败轮次不会覆盖成功轮次写入的缓存。

当前缓存仅存于进程内，常规替换程序并重启会清空旧缓存；无需迁移数据库或修改缓存格式。修复后持续失败的查询会在后续轮次重新尝试，数据库请求量可能高于原先错误地命中部分缓存的情况，现场需观察这一预期变化。

**4. B2：自定义查询完整读取后才交付结果**

在 `queryDynamicDatabase` 的读行循环后检查 `rows.Err()`。出现错误时返回 `nil` 和带 `%w` 包装的错误，保留 `errors.Is` 对超时、取消等原因的识别能力。

采用“单条 SQL 完整成功后才使用其结果”的规则：失败查询的部分行全部丢弃，避免把缺失的结果当作完整指标。该规则与当前 Query/Scan 失败时的处理一致；完整零行仍返回空结果和 nil error，不补零样本。

`CustomMetrics.Collect` 接收错误后调用现有 `HandleDbQueryErrorWithSource`，带当前轮次日志上下文，然后按现有循环继续其他配置项。已经完成的其他查询结果保留；后续查询仍受原共享查询上下文和数据源状态约束，不承诺在超时或降级后一定成功。自定义采集器本轮仍为 `unknown/legacy_unclassified`，业务错误通过关联 ERROR 与观察计数呈现。

新识别到的读行错误可能触发现有确认性健康检查或快速降级，这是原错误处理链现在收到真实错误后的预期行为。业务 SQL 不新增主动重试；测试分别核对业务查询次数与健康检查次数，不能把所有失败场景的总调用数一概要求与旧实现相同。

验收覆盖：完整成功、完整零行、Query 错误、Scan 错误、首行前读行失败、一行后读行失败、可解包的 deadline/canceled 错误，以及“失败查询 + 成功查询”的组合。通过适配器验证错误包含 `scrape_id/datasource/collector`，失败查询不输出部分样本。

**5. B3：默认汇总展示前 20 项，完整明细使用 DEBUG**

使用包内常量将 `zero_sample_collectors` 展示上限固定为 20，首版不新增配置项。INFO 与 WARN 的 `scrape_finished` 均应用同一上限，避免异常轮次重新产生无限名单。

| 字段或事件 | 实施后的规则 |
| --- | --- |
| `zero_sample_runs` | 全量零样本计数，截断前计算 |
| `zero_sample_collectors` | 按现有 scope、datasource、collector 顺序稳定排序后取前 20 项 |
| `zero_sample_collectors_omitted` | 新增整数，等于全量零样本数减去已展示项数；未省略时为 0 |
| `known_failed_runs` 等分类计数 | 按全部结果计算，不能从截断名单推导 |
| `slowest` | 继续保留最慢三项，排序和语义沿用现有实现 |
| `collector_finished` | 复用现有逐项记录：正常项 DEBUG，异常/慢项 WARN；启用 DEBUG 后可以按轮次汇集全部零样本项 |

不新增“全量零样本数组”的 DEBUG 事件，避免复制现有逐项信息及生成另一条大日志。默认名单中未出现的异常项仍有独立 WARN 完成记录和原始错误。是否省略明细本身不提高日志级别，也不改变任何执行状态、业务结果或样本。

该限制约束零样本列表的项数，不宣称整条日志拥有固定字节上限；字段字符串长度、不可用数据源列表和真实异常日志仍可能增加体积。实测日志字节数并记录规模，不在首版引入全面截断机制。

验收覆盖 0、1、20、21、1000 个零样本项：展示数为 `min(N,20)`、省略数为 `max(N-20,0)`，计数完整且排序稳定；最慢三项保持正确；被省略的失败项仍有 WARN 明细；启用 DEBUG 可恢复全部 N 项。保留“正常 INFO 每轮仅两条新增诊断事件”的检查，更新原“全部零样本都在 INFO”测试语义。

**6. B4：注册入口改用局部列表**

在 `RegisterMultiSourceCollectors` 内创建局部 `collectors`，保持现有采集器选择、顺序、构造及自定义配置预加载逻辑。列表完成后交给 `scrapeCollector.children`，交付后不再修改列表；可直接赋值，去掉仅为隔离包级列表而存在的额外切片复制。

删除 `collector_model.go` 的包级 `collectors`、`registerMux` 及无用的 sync 导入，保留 `MetricCollector` 接口需要的 prometheus 导入。移除注册函数中的对应 Lock/Unlock，不删除其他用途的锁。

优先复用现有注册与并发抓取测试，并做全仓引用检查和竞争检测。确认独立 Registry 的注册不会串用列表，同一 Registry 的重复注册沿用原有报错语义；本轮不引入动态注册、热重载或重复注册幂等机制。测试中的全局配置必须在并发开始前固定，不能通过并发修改全局配置制造与本次清理无关的竞争。

**7. 测试基线与验收方法**

原 `collection_business_baseline.json` 保存历史源码行为，其中包含坏缓存残留等已确认缺陷。本轮需要有意修正这些路径，不能为了保持历史快照一致而保留缺陷，也不能用新实现整体覆盖基线来消除差异。

- 保留历史基线文件。未受影响的正常、慢、错误、有效缓存等场景继续按原样本、标签、值与 SQL 次数比较。
- 将表空间和数据文件的具名 `cache recovery` 场景改用明确的新预期验证，检查样本只来自新查询、无残留标签或额外行，并保持预期业务查询次数。限定这两个场景，不能扩大为跳过全部错误或缓存测试。
- 更新结果分类测试中 `cache_recovery_unverified` 的旧预期，分别验证新查询 success/empty/partial/failed 与回退标记。
- 增加跨轮次缓存验证和自定义读取中断验证，防止单轮样本比较遗漏错误缓存与静默丢错。
- 对日志截断使用数量边界、排序和明细可恢复性断言；无需对耗时毫秒数或整行文本建立易变快照。
- 复用现有并发隔离、fast 超时后停止写入、后台排空、慢阈值与日志级别独立性测试，避免重复构建执行器测试体系。

**9. 现场验收与回滚**

自动检查通过后，在测试或低风险 DM 实例验证正常抓取、读取错误及恢复。正常输入比较指标名称、类型、标签和值；动态值按相同采样条件判断，不要求不同时刻机械相等。业务修复的预期差异单独记录：部分读取不再进入缓存，自定义失败查询不再交付部分行，坏缓存回退不再产生残留样本。

现场至少完成：正常连续三轮；表空间读取失败后恢复的重新查询和随后缓存命中；自定义查询读取失败的关联错误；INFO/DEBUG 切换后完整明细可查；目标数据源规模下单轮日志条数、字节数和采集耗时比较。难以安全制造的读行中断场景可以保留模拟驱动证据，但必须标明现场未验证。真实 DM 的 fast 取消与后台退出仍按前阶段待验项验证，不能由本次单元测试替代。

上线前保存现场当前程序、有效配置及对应版本。发现非预期指标丢失、采集卡住、竞争、异常查询增长或无法接受的日志开销时，停止推广并恢复现场原程序，按需恢复配置后重启。重启清空进程内缓存，无数据库结构回滚；回滚到旧程序也会恢复旧的完整性缺陷，应在记录中说明。面板单独回滚。

**10. 完成标准**

两处业务缺陷均有正式回归测试并通过；失败结果不跨轮缓存，自定义读行错误不再静默成功；默认零样本明细有上限且省略可识别，DEBUG 可恢复全量；注册入口无无用共享状态；正常路径兼容性和执行器边界测试通过；文档口径与代码一致；交付记录明确区分本地验证、现场验证与待办事项。
