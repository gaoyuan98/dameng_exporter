# 达梦 Exporter 采集诊断实施方案（收敛版）

阶段说明：本文保留采集诊断第一阶段的约定和验收背景。后续业务修复与收敛见[问题修复与收敛实施方案](采集诊断问题修复与收敛实施方案.md)；其中已替代本文的“部分读取仍可写缓存”“坏缓存回退可能残留”和“默认全量零样本名单”约定。当前使用行为以[采集日志排查指南](采集日志排查指南.md)为准，本文历史示例不作为后续版本的验收标准。

初稿日期：2026-11-10。修订日期：2026-11-12。状态：代码实施、本地自动验收和实施后审查完成；真实 DM 现场验收与正式发布待执行，详见[实施验收记录](采集诊断实施验收记录.md)。

本方案以当前工作区已有的日志初版为基础，交付一版可以直接用于现场排查的采集日志。现有初版已具备轮次编号、日志上下文和采集器计时；本文规定接下来必须完成的收敛改造、代码位置、返回分支、测试和发布步骤。方案中的日志是预期示例，不代表现场已经产生，也不代表以下改造已经完成。

## 1. 交付目标与范围

第一批交付后，默认 INFO 日志应能回答：本轮采集用了多久；哪个数据源的哪个采集器最慢；哪些错误属于这一轮；没有指标时，已确认失败与尚未判定分别有哪些。

| 本次必须交付 | 实现边界 |
| --- | --- |
| 全部采集器的轮次关联和整体计时 | 保留每次 `scrapeCollector.Collect` 的独立轮次；包括内置、自定义和公共采集器 |
| 简短的轮次汇总 | 总耗时、样本数、分类计数、最慢三项、零样本采集器名单、当前不可用数据源；不在 INFO 重放全部结果 |
| 异常和慢采集器明细 | 原始错误带轮次；异常完成记录带实际模式、生效预算、耗时、执行状态和业务结果 |
| 四个重点采集器的明确结果 | `TableSpaceInfo`、`TableSpaceDateFileInfo`、`DBSessionsStatus`、`DBSystemInfo`；其余业务结果为 unknown |
| 一个慢提示配置 | 全局 `collectorSlowThresholdMs`，默认 5000，显式 0 关闭提示 |
| 测试和使用文档 | 并发隔离、快速超时、结果语义、配置兼容及现场验收步骤 |

本次保留现有 Registry、HTTP 入口、SQL、查询预算、缓存格式与有效期、健康降级条件和采集模式。诊断指标、SQL 逐条计时及已发现的业务缺陷分别交付，不作为第一批的依赖。

耗时粒度是“采集器整体”：包含前置连接检查、连接获取、查询、读行、处理、错误处理及前台转发。多条 SQL 共用一个采集器时，本次只能定位到该采集器，不能据此宣称知道每条 SQL 或数据库服务端的执行时间。

## 3. A1：结果契约与计时口径

### 3.1 最小接口

新增可选接口，保留现有 `MetricCollector` / Prometheus 接口：

```go
type ResultCollector interface {
    CollectWithResult(chan<- prometheus.Metric) CollectorOutcome
}

type CollectorOutcome struct {
    State         OutcomeState // success / empty / partial / failed / unknown
    Reason        string       // 固定原因码，不放原始错误正文
    DataOrigin    string       // database / cache / unknown
    CacheFallback bool         // 是否经历缓存解析失败后的查询回退
}
```

四个采集器把现有业务主体移入 `CollectWithResult`，原 `Collect` 只调用它并忽略返回值。执行器通过类型断言二选一调用，不先调用 Collect 再调用 CollectWithResult。旧采集器不实现接口，照常执行，返回 unknown / legacy_unclassified。

`collectionResult` 保存独立字段 `execution` 与 `outcome`，替换现有从日志数量推断出来的单一 `status`。日志 Hook 只计数，不参与业务结果判定。原始错误仍由现有错误位置输出，不在结果结构中保存或重复打印整段错误正文。

### 3.2 状态定义及优先级

| 场景 | execution | outcome | reason / 说明 |
| --- | --- | --- | --- |
| 明确契约正常完成 | completed | success | 完成该采集器现有业务契约 |
| 查询完整成功、按业务允许没有输出 | completed | empty | 不能由 samples=0 推断 |
| 读取不完整但已生成可用的部分结果 | completed | partial | scan_error 或 rows_error |
| 查询或读取失败，未形成可用业务结果 | completed | failed | query_error、query_timeout、scan_error、rows_error 等 |
| 未迁移的采集器返回 | completed | unknown | legacy_unclassified；有无错误日志均不改变它 |
| 适配器前置检查失败 | skipped | unknown | datasource_unavailable；业务采集没有启动 |
| 快速模式前台预算到期 | timeout | unknown | frontend_timeout；冻结时查询可能仍未结束 |
| 执行期间捕获 panic | panic | failed | panic；保留原异常和堆栈 |

具体规则：

1. 查询主动返回超时错误，是 `completed / failed / query_timeout`；快速模式先返回，是 `timeout / unknown / frontend_timeout`，两者分开记录。
2. `partial` 由采集器判断业务读取完整性；转发丢弃单独记 `dropped_samples`。即使业务为 success，只要丢弃过样本，也不能称本轮完整采集成功。
3. query_timeout 使用错误类型及查询上下文判定。未核实的 DM 错误码不做字符串猜测；权限错误先归为 query_error，具体对象和权限原因保留在原始错误中。
4. 缓存命中、无记录占位等不能证明完整性的路径采用 unknown，第 5 节逐项规定。
5. 日志级别不得参与业务分支、结果分类、取消或丢弃策略的决策。同一已完成业务路径的 outcome 按契约判定，日志计数仅统计实际观察到的日志。计时记录实际经过时间，不要求不同级别下数值相同；fast 的超时与非阻塞转发受调度影响，不要求每次 execution 和样本集合完全一致。分模式验收见第 7.1 节。

### 3.3 结果所有权

- 每次 Collect 创建一个局部 `collectionRound`；每个实际运行的“数据源＋采集器”只有一条前台完成记录。
- 执行器是完成记录的唯一写入者。worker 通过容量为 1 的结果 channel 报告返回值或 panic，不能直接修改轮次汇总。
- 完成时复制字段、样本计数和日志计数后追加到 round；后台不再持有可修改该记录的引用。
- 汇总对副本排序：耗时降序，再按 datasource、collector 排序，保证并列结果稳定。最慢三项不足三项时全部展示。
- 以 `recorded_runs` 表示实际记录数，不声称等于“应执行任务数”。数据源未进入健康池列表时，不伪造几十条 skipped 记录。
- scope 和 datasource 按实际注册与执行方式确定，见下表；未迁移者保持 unknown，计入汇总，避免统计时忽略部分工作。

| 采集器或入口 | scope / datasource | 每轮记录方式 |
| --- | --- | --- |
| 经 MultiSourceAdapter 执行的内置采集器，包括 DmapProcessCollector | database / 当前数据源配置名 | 每个实际进入执行流程的数据源各一条；主机进程采集不能清空 datasource |
| CustomMetricsMultiSourceAdapter | database / 当前数据源配置名 | 每个实际执行自定义采集的数据源各一条，保留原 blocking 行为 |
| BuildInfoCollector | exporter / 空字符串 | 公共入口整体一条 |
| DatasourceHealthCollector、DbNodeTypeInfoCollector | exporter / 空字符串 | 各自整体一条，样本数为其遍历数据源生成的总数；不拆成虚构的逐源耗时 |

scope 描述诊断执行入口；database 包含经数据源适配器执行的主机进程采集。公共记录的 datasource 为空，不影响其业务指标原有的 datasource 标签。公共采集器由本轮外层记录日志与 panic，不向共享实例写入可变的轮次上下文，防止并发抓取串号。

### 3.4 统一时间与样本定义

| 字段 | 起止位置 |
| --- | --- |
| `collection_duration_ms` | 进入本轮 Collect 到全部前台完成、转发停止并形成快照；不包括 HTTP 编码、传输和后台继续执行 |
| `duration_ms` | 创建该采集器 run、开始前置检查，到前台完成且停止转发 |
| `background_duration_ms` | 原 run 开始到超时后的 worker 真正退出，是总时长，不是额外耗时 |
| `samples` | 成功转发给本轮 Registry channel 的现有业务样本数；不是承诺客户端已收到的数量 |
| `dropped_samples` | 前台快速模式非阻塞转发中已确认丢弃的数量；不把返回后的后台丢弃量追加入已冻结结果 |

并发采集器的耗时不能相加作为整轮耗时。`samples=0`、查询失败和合法无数据分别解释；采集结束日志不推断 HTTP 抓取成功。

完成记录还固定以下执行信息，并带入默认可见的慢项、异常项和最慢三项：

| 字段 | 定义 |
| --- | --- |
| mode | fast、blocking，或公共入口的 direct；自定义采集按实际行为记录 blocking |
| timeout_ms | 本项 fast 使用的前台等待预算；blocking、direct 或未启用该预算时为 0，不把查询自己的取消预算混入此字段 |
| timeout_scope | 启用 fast 预算时为 worker，其余为 none；若 execution=skipped，表示该预算未进入计时阶段 |

mode 和预算在前置检查前固定，即使检查失败也保留。duration_ms 从前置检查开始，而 fast 预算沿用现有 worker 阶段的计时起点，因此总耗时可能大于 timeout_ms。该预算不覆盖 HTTP 编码、传输和整个转发阶段；具体等待边界见第 4.3 节。

## 4. A2、A3：配置及执行流程

### 4.1 配置落点

新增全局配置，放在 TOML 的数据源表之前：

```toml
collectorSlowThresholdMs = 5000
```

| 文件 | 必须修改的内容 |
| --- | --- |
| `config/multi_config.go` | MultiSourceConfig 增加字段；DefaultMultiSourceConfig=5000；ValidateAll 拒绝负数及转为 time.Duration 会溢出的值；StringCategorized 展示实际生效值 |
| `config/toml_parser.go` | raw 字段使用 `*int`；toConfig 从默认配置复制，只有非 nil 才覆盖，因此未配置为 5000、显式 0 保持为 0 |
| `config/global.go` | 增加只读 getter；无全局配置时返回默认值，有配置时原样返回，不能把 0 当成缺失 |
| `docs/config/dameng_exporter.toml` | 增加字段和“只控制提示、0 关闭”的注释 |

`ApplyAllDefaults` 不为该字段执行“零值补默认值”。程序内直接构造结构体时 0 同样表示关闭，需要默认值的调用方从 DefaultMultiSourceConfig 复制。命令行合并沿用已加载配置中的该字段，不新增命令行开关；合并命令行、保存配置及自动加密密码后都必须保留该值。

### 4.2 慢提示独立运行

1. run 创建时读取并固定本次慢阈值，从前置检查开始计时。
2. 阈值大于 0 时启动一个轻量观察任务：定时器到期且 run 尚未结束，只输出一次 `collector_slow`；不取消、不中断、不降级数据库。
3. 前台结束时停止观察任务并等待其退出，再冻结记录，防止慢提示晚于本轮结束输出。最终 slow 按实际 duration 与阈值比较；刚好完成时可以只记录完成明细而没有“仍在执行”提示。
4. 阈值为 0 不创建观察任务，slow=false；总耗时和最慢三项照常记录。
5. 原来借用 queryTimeout/globalTimeoutSeconds 判慢及重复的慢提示删除。快速模式的实际超时仍使用现有 globalTimeoutSeconds；查询自己的取消预算保持原路径。

观察任务不计入采集器业务结果，也不通过自身 WARN 日志反向增加 observed_warning_logs。执行器诊断事件使用带相同关联字段、但不带业务日志 Hook 的 logger；业务错误使用带 Hook 的 logger。

### 4.3 普通完成、超时及后台退出

保留当前适配器的缓存 channel 和转发方式。只在现有执行位置接入返回值和诊断，不将前置检查、HTTP 等待等重新纳入快速模式的取消预算。

```text
创建 run、固定实际 mode 和预算、日志上下文、慢观察任务
  → 原前置连接检查
  → 创建转发者和 worker
  → worker 调用 CollectWithResult 或原 Collect（二选一）
  → 等待 worker / 现有快速模式到期
  → 确认停止向本轮 channel 转发
  → 停止慢观察任务
  → 冻结一次完成记录、输出完成事件、追加本轮结果
```

实现要求：

- worker 的 defer 捕获 panic、关闭 safeChan，并向有缓冲的结果 channel 发送一次结果；不能依赖前台仍在等待，不能由前台关闭 worker 所用的 channel。
- 正常路径等待 worker 返回及 forwardDone，取真实业务结果；blocking 模式继续等待，不因慢阈值或原全局等待阈值强行返回。
- fast 到期后，先通知转发者停止写 Registry channel，再等待 forwardDone 确认；转发者确认后可继续在后台排空 safeChan，让 worker 能退出。
- fast 前台记录固定为 timeout / unknown；worker 后续返回不能改写它。独立后台等待者取最终结果，输出 `collector_background_finished`，仍使用原 scrape_id、datasource、collector。
- 当前快速预算从原有 worker 阶段起算；worker 已完成、正在等待转发结束时不追加新的取消行为。此处保持现有预算边界，不能将日志改造变成“整次 HTTP 硬超时”。
- 完成和超时同时就绪时，若已能取得 worker 完成结果则优先使用完成路径；否则按真实前台超时记录。测试使用同步信号控制顺序。
- 一旦前台结束，任何后台事件都不能再次向该轮 Registry channel 写样本，也不能追加第二条前台完成记录。

`CustomMetricsMultiSourceAdapter` 继续实际使用 blocking，日志记录实际模式；不因全局 fast 而修改自定义采集原有行为。公共采集器也加入计时和 panic 归属，但不强加数据库前置检查或 fast 超时。

## 5. A4：四个采集器逐分支实施

### 5.1 表空间与数据文件

文件：`collector/db_tablespace_info_collector.go`、`collector/db_tablespace_datafile_info_collector.go`。

保持现有逐行读取、有效行输出和缓存写入流程；增加局部结果变量，记录读取错误和新查询取得的有效行数，不由日志条数判断。

| 返回分支 | 结果 | 实施说明 |
| --- | --- | --- |
| 缓存解析成功并使用 | unknown / cache_unverified | data_origin=cache；旧缓存没有完整性标记，包括空缓存都不能断言 success 或 empty |
| 无缓存；查询及完整读取成功，有记录 | success | data_origin=database |
| 无缓存；查询及完整读取成功，零记录 | empty | 无业务输出；区别于读取错误导致的零记录 |
| 采集器内部连接检查失败 | failed / datasource_unavailable | 与适配器尚未启动业务时的 skipped 区分 |
| Query 返回错误 | failed / query_error 或 query_timeout | 保留原错误处理和降级调用 |
| Scan 或 rows.Err 失败，仍输出部分有效结果 | partial / scan_error 或 rows_error | 如同时存在，固定优先 rows_error；不把部分结果说成成功 |
| Scan 或 rows.Err 失败，无可用结果 | failed / scan_error 或 rows_error | 不判 empty |
| 缓存解析失败后，查询及读取正常完成 | unknown / cache_recovery_unverified | cache_fallback=true；见下方现有代码限制 |
| 业务读取完整且已输出，仅缓存序列化失败 | 保留对应业务结果 | 错误照常记录；缓存保存失败不自动等同业务采集失败 |

现有缓存解析失败时只清空局部 cachedJSON 字符串，未清空可能被部分反序列化填充的结果切片；后续查询会继续追加。因此，首批不能仅因回退 SQL 成功就报告 success。缓存回退清理与“部分读取仍写缓存”合并为独立缓存修复；完成该修复和测试后，再将已证明完整的恢复路径升级为 success/empty。

新增测试覆盖：正常多行、零行、Query 超时、Scan 中途错误、rows.Err 中途错误、全行无效、旧缓存命中、空缓存、缓存解析失败且切片被部分填充、缓存序列化失败。核对两个采集器分别保持每条有效记录原有的 3 个、2 个业务样本。

### 5.2 会话状态

文件：`collector/db_sessions_status_collector.go`，扩展现有 `collector/db_sessions_status_collector_test.go`。

- 查询并完整读取成功：success。
- 成功但零记录：success，沿用 ACTIVE/IDLE 补零，不能判 empty。
- Query、Scan 或 rows.Err 失败：failed，按错误阶段给 reason。
- 由于现有实现完整读取后才输出，Scan 中途失败即使已读到若干行，仍为 failed；不输出部分结果，不补零，也不判 partial。
- 连接检查失败：failed / datasource_unavailable。

每个失败测试同时断言没有伪造的 ACTIVE/IDLE=0；调用新接口和旧 Collect 的业务样本一致，每次采集只执行原有一次业务查询。

### 5.3 系统信息

文件：`collector/db_system_info_collector.go`，新增相应结果测试。

- 读取一条系统信息成功：success；NULL 字段继续按现有逻辑省略对应 CPU/内存指标，不擅自新增必填要求。
- Query、Scan、rows.Err 或连接检查失败：failed，保留原来的提前返回。
- 没有记录且没有错误：当前代码仍输出数值为 1、信息标签为空的基础指标。本期保留该样本，结果为 unknown / no_row_placeholder；不能说 empty，也不能将占位指标视为已验证成功。
- 保留现有仅读取首条系统信息的行为，不顺带修改 SQL 或新增查询。

测试同时覆盖正常值、NULL、无记录占位和各失败阶段，分别比对业务指标集合。

## 6. A5：日志格式与统计规则

### 6.1 固定事件与级别

| 事件 | 级别及次数 | 内容 |
| --- | --- | --- |
| scrape_started | INFO，每轮一次 | scrape_id、phase=collection |
| collector_started | DEBUG，每项一次 | 数据源、采集器、实际 mode、timeout_ms、timeout_scope |
| 原有业务错误 | 沿用原级别 | 增加当前轮次和采集器关联；保留原错误原因 |
| collector_slow | WARN，达到阈值仍未结束时至多一次 | mode、timeout_ms、timeout_scope、duration_ms、threshold_ms、still_collecting=true |
| collector_finished | 普通完成 DEBUG；异常或 slow 为 WARN，每项仅一次 | mode、timeout_ms、timeout_scope、execution、outcome、reason、duration_ms、samples、dropped_samples、slow、观察到的业务日志计数 |
| scrape_finished | 普通 INFO；存在异常、观察到 WARN/ERROR、slow 或不可用源时 WARN，每轮一次 | 第 6.2 节的短汇总 |
| collector_background_finished | INFO，发生前台超时后的 worker 退出时一次 | 原 mode、timeout_ms、timeout_scope、background_duration_ms、最终后台 outcome；不更新前台记录 |

采集器完成的异常条件包括：failed/partial、timeout/panic/skipped、丢弃样本、观察到业务 WARN/ERROR。unknown 本身不升级为 WARN。超时信息归入 collector_finished，不再额外输出一条正文重复的 collector_timeout。

关联字段统一为 scrape_id、scope、datasource、collector。datasource 为配置名称；若实际业务指标 datasource 标签不同，补充 datasource_label，使用 `buildLabelContextFromPool` 的既有解析结果。完成事件使用平铺字段，明确结果还带 data_origin、cache_fallback；不再套一层 result。保留原始错误正文，不再在同一日志内新增含义相同的 data_source 字段。

正常情况下新增的 INFO 诊断日志固定为每轮两条；后台健康检查、启动消息和原有真正异常单独存在，不把“新增两条”宣传为整个进程只输出两条日志。周期性缓存命中等正常提示放在 DEBUG。

A5 必须检查运行期绕过 logger 的错误输出。已确认的落点是 `collector/host_process_info_collector.go` 的 checkProcess：命令执行失败后当前使用 fmt.Printf 并返回 0。实施时改为使用本次采集的 c.log() 输出 ERROR，保留错误和 process_name，使文件日志包含 scrape_id、datasource、collector，并进入 observed_error_logs。该路径仍按现有逻辑返回 0，不在日志任务中修改业务指标值；因为该采集器未迁移结果契约，outcome 仍为 unknown，但完成记录和轮次汇总须因观察到错误而可见。启动及独立后台健康消息不强行绑定采集轮次。

### 6.2 轮次结束字段

| 字段 | 计算规则 |
| --- | --- |
| phase | 固定 collection，避免冒充 HTTP 全链路结果 |
| collection_duration_ms | 第 3.4 节的整轮前台耗时 |
| recorded_runs | 本轮完成记录数，含公共采集器，不含从未进入执行流程的任务 |
| samples | 所有记录实际转发的现有业务样本之和 |
| known_failed_runs | outcome 为 failed/partial，或 execution 为 timeout/panic，或 dropped_samples>0 的记录；每项去重计一次 |
| unknown_runs | outcome=unknown 的记录数；与 known_failed_runs 可重叠，例如 fast 超时 |
| observed_error_runs | observed_error_logs>0 的记录数；独立于业务结果，恢复后仍可能有错误线索 |
| skipped_runs | 前置检查失败、业务未启动的记录数；不能归入业务成功 |
| slow_runs | slow=true 的记录数 |
| zero_sample_runs | samples=0 的实际完成记录数，含 skipped、合法 empty 和 unknown；不等于失败数 |
| zero_sample_collectors | 所有零样本记录的简短名单，仅列 scope、datasource、collector、execution、outcome、reason；按 scope、datasource、collector 排序，无记录时为空数组 |
| unavailable_datasources | 汇总时处于不可用状态的已启用数据源名称，去重排序；它是结束时快照，不代表整轮都不可用 |
| slowest | 最慢三项，含 scope、datasource、collector、mode、timeout_ms、timeout_scope、duration_ms、samples、execution、outcome |

零样本名单独立于最慢三项，即使某项耗时很短、没有报错、结果为 unknown，也必须在 INFO 汇总中能查到名称。名单只列零样本项，不重放其完整结果或其他正常项，本期不截断该名单、不新增条数配置；若单轮日志过大，应在试运行中发现并处理，不能静默漏项。日志级别仍由异常规则决定，零样本或 unknown 本身不升级为 WARN。未进入执行流程、没有记录的任务不加入名单。

不再输出默认全量 results 数组；DEBUG 下每项 collector_finished 已能恢复本轮明细。计数不是互斥分区，文档不得引导用户相加求总数。汇总出现 unknown 不等于故障数，也不代表所有未执行任务都已被统计。

## 7. A6：测试与验收

### 7.1 自动测试清单

优先扩展现有 `collector/collection_log_test.go`，增加 `collector/collection_result_test.go`、`collector/collection_outcome_test.go` 和 `config/collector_diagnostics_test.go`；会话分支继续放在原测试文件。新增测试必须验证行为和失败边界，不只比对实现字段。

| 用例 | 必须验证的结果 |
| --- | --- |
| 两轮并发、两个数据源、交错错误 | ID 独立；每条错误与完成记录只属于原轮次；快照互不覆盖 |
| 旧采集器无输出、有输出、报错后返回 | 都保持 unknown；不能从日志数、样本数推断 success/failed |
| 第 5 节全部返回分支 | 明确结果符合各自业务契约，缓存和占位路径不伪造成功 |
| 日志级别 INFO/ERROR/DEBUG | 阻塞模式在固定输入下的业务结果和指标集合一致；fast 按下方规则验证策略、计数和边界，不断言每次耗时或样本集合相同 |
| fast 超时后再产生指标和错误 | 从预算实际起点验证到期后走停止转发路径；确认 forwardDone 后不再写本轮；后台关联原 ID；只冻结一次，不把整项耗时当作预算本身 |
| fast 转发丢弃，但业务完整成功 | outcome 可以 success；dropped_samples>0，known_failed_runs 必须计入一次 |
| worker panic、公共采集器 panic | 原因归属正确；关闭与等待有序，不导致挂起或重复完成 |
| blocking 查询持续超过慢阈值 | 提示一次；仍等查询完成并转发样本，不按慢阈值取消 |
| 慢阈值小于或大于 fast 预算 | 按实际先后记录慢或超时；不为等待慢提示延迟前台返回 |
| 前置检查慢或失败 | 总耗时包含检查；慢提示有效；失败为 skipped，业务查询未调用 |
| 自定义采集在全局 fast 下运行 | 保持原 blocking 行为，记录实际模式 |
| 两个数据源的主机进程采集交错运行 | 各自保留 scope=database 和正确 datasource；日志不串源；公共记录不能代替逐源记录 |
| 公共健康和节点类型采集 | 每个公共入口每轮一条 scope=exporter 记录；业务指标中的逐源标签与原样本不变 |
| 主机进程命令执行失败 | 用测试替身触发命令错误，验证结构化 ERROR 含原轮次、数据源、采集器和进程名；错误计数增加，完成记录仍为 unknown，原有返回零行为不变 |
| 非最慢项零输出且无错误 | 该项即使不在 top3、完成明细仅 DEBUG，INFO 的 zero_sample_collectors 仍含其名称和结果；合法 empty、skipped 可区分；名单不漏项，零样本不自动告警 |
| 正常一轮及持续单项权限错误 | 新增正常 INFO 轮次日志两条；异常不会带来全量健康项重放；top3 排序稳定 |
| 全部数据源不可用 | 汇总列出不可用源；无虚构任务或旧成功记录；公共健康指标保持原行为 |
| 缺省、0、正值、负值、溢出配置 | 缺省=5000；0 不复原；非法值启动校验失败 |
| 配置加载、命令行合并、保存、密码自动加密 | 新参数及显式 0 均保留；现有参数不受影响 |
| 同一固定输入的新旧业务采集比较 | blocking 下比较完整指标名、类型、标签、值、样本集合和 SQL 调用数；fast 下比较原有非阻塞策略与受控时序的计数、超时安全边界 |
| 模式和预算在 INFO 可见 | 异常完成记录与最慢三项包含实际 mode、timeout_ms、timeout_scope；自定义项不误报 fast，skipped 保留预算信息，公共项为 direct/0/none |

用可控制列数、Scan 错误及中途 rows.Err 的模拟数据库驱动覆盖四种查询结构；不能将会话测试的两列数据直接用于其他采集器。测试中使用同步 channel 控制并发时序；涉及全局 config、logger、缓存的用例清理还原状态，不使用共享全局的 t.Parallel。

按模式固定验收方法：

- blocking 与 direct：固定输入和可控业务返回路径，比较完整业务样本与明确结果；计时只验证覆盖了实际等待、结果非负及合理误差，不比较不同运行的精确毫秒值。
- fast：使用受控接收者分别制造可转发、不可转发和超时，验证策略与实际计数。未超时且 worker 完整结束的受控测试，应满足 samples+dropped_samples=生成样本数；超时测试中，后台排空量不追加入前台计数，不套用该等式。
- fast 在超时边界附近可能因调度、日志开销发生完成/超时或转发/丢弃差异；验收关注已有策略未被改变、计数如实记录、只完成一次且无返回后写入，不要求不同日志级别或新旧版本每次输出逐项相同。
- 慢提示与预算测试用同步信号证明时间先后，并设置合理的整体测试超时；不得依赖精确 5ms、20ms 等墙钟相等断言。持续耗时变化记录基线后分析，不将正常调度抖动判为功能失败。

执行以下检查并保存结果：

```bash
go test ./...
go test -race ./collector ./config ./db ./server ./utils
go build -o /tmp/dameng_exporter-diagnostics .
```

编译环境需支持 race；模拟驱动的通过记录不能代替真实 DM 取消行为验证。上述是实施阶段的验收命令，不表示本文修订时已执行了尚未实现代码的测试。

### 7.2 现场试运行步骤

1. 在测试环境保留原二进制、配置、面板 JSON，记录相同采集开关、缓存状态和模式下的旧日志及 `/metrics` 样本。
2. 替换候选二进制，先保持原配置运行，验证旧配置能加载，默认阈值为 5000ms。
3. 正常场景观察连续 3 轮：轮次唯一、开始结束对应；总耗时、实际模式与最慢项可读；零样本名单能查出非最慢项的零输出，主机进程错误保留数据源。blocking 下业务指标集合无非预期变化；fast 同时核对真实丢弃和超时记录。
4. 在测试数据源复现权限不足、慢查询和快速超时；每种至少取得一轮完整事件。按 scrape_id 能串起具体错误、耗时、结果和后台退出。
5. 临时启用 DEBUG 验证正常项明细齐全，再恢复 INFO；检查单项持续错误不会每轮重放所有健康项。
6. 用固定输入比较 SQL 次数，确认诊断没有额外访问数据库；样本兼容性按第 7.1 节区分 blocking 与 fast。记录耗时、单轮日志大小和日志量变化，验证零样本名单完整可读，有明显回归则查明原因再发布，不设没有基线的统一百分比门槛。
7. 真实 DM 中若查询取消后仍持续运行，保留后台退出证据，转独立任务处理；不能把新增日志视为已经修复该行为。

### 7.3 发布、文档与回滚

交付包包含候选二进制、配置样例、测试记录和更新后的 `docs/documents/采集日志排查指南.md`；README 链接继续指向排查指南。指南必须说明四项结果覆盖范围、unknown、缓存路径、零样本名单、实际模式与预算起点、计时口径、主机/公共记录归属和日志筛选方法，并替换初版 status/results 字段说明。

| 指标 | 规则 |
| --- | --- |
| dameng_exporter_collector_duration_seconds | 本轮前台耗时，毫秒换算为秒；不输出未执行任务的虚构 0 |
| dameng_exporter_collector_samples | 本轮实际转发的现有业务样本数，不把诊断指标自身计入 |
| dameng_exporter_collector_success | timeout/panic/丢弃优先为 0；completed 且 success/empty 为 1，partial/failed 为 0；普通 unknown 或 skipped 不输出 |

使用本轮不可变快照生成 ConstMetric，不设置全局“上轮结果”Gauge。沿用现有数据源及静态环境标签，只增加稳定的 collector 维度，不加入 scrape_id、错误正文或 SQL。描述符遵循现有 Registry 的注册和标签规则，不另建每请求 Registry。

独立验收：并发响应不串值；普通 unknown 不输出 success；未执行不输出旧成功值；明确失败输出 0；新旧 datasource 身份可匹配；不存在重复序列。小型面板只展示耗时排行、趋势、样本数及已评估成功状态，缺少 success 显示“未评估”。

### 8.2 采集器总耗时仍不足以定位时，才加 SQL 计时

先从最慢三项定位采集器。如果该采集器有多条 SQL 且无法分清，再为该项添加固定 query_id 和总计时，覆盖 Query/QueryRow、Scan、结果迭代及 rows.Err，元数据和回退查询也要标识。仍不称为数据库服务端时间，不默认引入显式 DB.Conn 分段和全量 SQL 包装框架。

### 8.3 已知业务问题分别修复

| 独立事项 | 修复入口 | 独立验证要求 |
| --- | --- | --- |
| 查询超时取首个数据源配置 | `config/global.go` 及调用处 | 两个数据源设置不同预算，分别生效 |
| 单项查询 deadline 使数据源降级 | `utils/db_util.go`、`db/pool_manager.go` | 真实复现后设计健康确认；不预设次数或并发阈值 |
| 不完整结果写缓存、损坏缓存回退残留 | 两个表空间采集器 | 部分读失败不污染有效缓存；回退不混入残留；之后才能提升缓存路径结果可信度 |
| 自定义查询未检查 rows.Err | `collector/custom_collector.go` | 中途读行失败被识别，原自定义模式不变 |
| 数据源间指标开关执行边界 | `collector/register_multi.go` 及适配器 | 两个数据源采用相反开关，核对实际执行集合 |
| 归档状态面板表达式 | `docs/dashboards/达梦监控面板_20251204.json` | 对照实际指标及 datasource 筛选验证归档状态 |

上述缺陷不被本方案的日志状态掩盖，也不捆绑为“诊断版本全部完成”的条件。
