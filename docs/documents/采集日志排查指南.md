# 采集日志排查指南

本指南描述当前源码中的统一 SQL 采集诊断行为。诊断阈值、日志级别与采集模式的配置见[参数配置指南](参数配置指南.md)。

## 配置与正常输出

在首个 `[[datasource]]` 之前配置：

```toml
logLevel = "info"
scrapeSlowThresholdMs = 30000
```

未配置阈值时使用 30000ms；0 关闭 `scrape_diagnostic` 与 `sql_top` 输出；明确 SQL 超时、fast 前台超时、panic 和错误仍独立记录，并计入最终摘要。负数、时长溢出或旧 `collectorSlowThresholdMs` 配置拒绝加载。没有新增命令行参数。`queryTimeout` 与 `globalTimeoutSeconds` 的现有行为不变。

通过项目注册入口采集时，正常 INFO 每轮只有一条 `scrape_finished`。这条记录总是 INFO，包括异常轮次；级别设为 WARN/ERROR 会过滤摘要。启动、数据源断连/恢复、独立错误和后台退出不属于正常摘要数量限制。

摘要包含 `scrape_id`、`phase=collection`、`collection_duration_ms`、`runs`、`skipped_runs`、`sql_calls`、`sql_unfinished_at_cutoff`、`sql_error_calls`、`samples`、`dropped_samples`、`issue_runs`、`frontend_timeout_runs`、`unavailable_datasource_count`。没有最慢采集器数组、零样本名单或 unknown 业务分类。零样本本身不表示故障。

## 慢或超时怎么定位

只有整轮耗时达到阈值且仍在采集时，本轮才输出一组 `scrape_diagnostic` 加最多五条 `sql_top`。SQL 错误、SQL 超时、前台超时或 panic 不绕过整轮耗时门槛；提前发生的异常不会消耗后续时长触发机会。每条排名包含实际 SQL 模板和独立调用编号，直接按 `scrape_id` 与 `snapshot_id` 关联，不需要查编号映射表。

排名包括已成功、失败和仍在执行的调用。`sql_duration_ms` 是进入 Query/Next/Scan/Err/Close/元数据等可观察 API 的累计时间；`sql_wall_ms` 还包括两次 API 之间的业务处理与转发等待。它们都不是服务端纯执行时间，并发 SQL 的耗时不能相加当作整轮耗时。

`sql_phase=query/next/scan/err/close/columns/column_types/row_scan` 表示当时进入的 API；`between_calls` 表示当前在两个 API 之间。QueryRow 的 Scan 内部取行与关闭不可拆分，统一为 row_scan，不伪造 next/scan/close 分项。

先看 Top 5 中此前成功但很慢的查询，再看错误调用的 `budget_remaining_ms_at_start`。例如 A 成功花掉 29 秒，B 启动只剩 1 秒后超时，A 仍保留排名，B 独立错误展示少量剩余预算。只能在同一 run 的实际 context 范围内比较预算链。当前多数采集器从全局首数据源读取 queryTimeout，慢 SQL 采集器使用注入的数据源配置；本次保留该既有差异，日志按实际 context 记录。

`sql_calls` 是应用进入数据库 API 的次数，包括进入时 context 已失效的尝试；database/sql 内部坏连接重试仍计一次。`context_state_at_start` 为 deadline_exceeded/canceled 时，不能凭日志断言 SQL 已发送到服务器。无 deadline 的预算为 null，耗尽为 0。

## 结束、后台与错误

每轮始终输出最终 `scrape_finished`。只有阈值大于 0 且结束时整轮耗时已达到阈值，才允许附最终 Top 5：没有进行中诊断时，由摘要充当总览；已有诊断时，只有候选集合、顺序、生命周期、结果或错误阶段变化才重打最终排名，单纯毫秒增加不重打。未达到阈值的异常轮次仍记录错误与摘要中的异常计数和原因，`top_refreshed=false`、`last_top_snapshot_id=0`。`top_count` 表示快照候选数量，不表示本次实际打印了排名。`last_top_snapshot_id` 与 `top_refreshed` 指向最后一组。诊断 INFO 最多 12 条，SQL 错误及后台退出另算。

fast 超时在 run 上冻结 SQL，`state=detached` 表示前台截止时调用未结束。停止转发并等待确认后冻结样本计数。该 worker 后续的 SQL、错误和结束属于 `phase=background`，保留原 `scrape_id/run_id`，不会改写本轮或下一轮摘要。`collector_background_finished` 表示后台函数确已退出；前台超时不证明数据库取消成功。

`sql_error` 独立于 Top 5，包含 SQL 模板、数据源、采集器、run/query、错误阶段、原始错误、耗时与初始预算。包装层是 SQL 错误的唯一出口，错误工具继续执行原健康检查和降级动作。精确声明的兼容探测失败可以是 DEBUG；仅写 purpose=probe 不会把权限、网络或未知错误降级。普通 SQL 错误不自动附堆栈，panic 显式附栈。

`active_stages` 反映 preflight/query/read_rows/process/metric_forward/error_handling/health_check/pool_close 等活动执行流；worker 和转发器各自记录，run 可以贡献多个阶段。Ping 与关闭连接池耗时属于采集阶段，不继续算到已返回的 SQL 上。

## 读取与 DEBUG 明细

`state=running/finished/detached` 与 `result=pending/ok/empty/error` 分开。`read_state=complete` 只证明调用点声明的 `read_scope=first_row/first_result_set` 已完成，不代表所有结果集。提前关闭为 partial；无法判断 QueryRow 扫描失败的读取范围时是 unconfirmed，行数为 null。Scan 首错不会被后续成功扫描或 Close 覆盖；Rows 记录等显式 Close 返回才终结。

DEBUG 输出全部 sql_started/sql_finished、采集器计数与阶段；前置检查跳过时，collector_finished 带 run_state=skipped 和 skip_reason。INFO 只留全量计数、活跃调用和终结前五。事后切换 DEBUG 无法补回此前未输出的 SQL 历史。

文件使用无颜色 JSON、毫秒时间；控制台单独编码。SQL 换行、制表符、引号和控制字符采用可逆转义，一条事件一个物理行，不截断模板。绑定参数和结果集不进入 SQL 诊断日志；模板自身的字面量仍会保留。

## 验证范围

当前自动化测试使用模拟驱动和可控时钟，尚未完成真实 DM 环境中的慢查询、权限失败、驱动取消及后台退出验证。逐 SQL 跟踪增加了 CPU 与内存分配开销，生产规模下的开销仍需实测；日志条数减少不代表整体性能提升。
