# 采集日志排查指南

控制台使用中文摘要，文件保留英文事件名和结构化 JSON。两者来自同一事件：例如一条 `sql_error` 在控制台显示错误摘要和 SQL 详情两行，在文件中仍是一条 JSON。日志级别与采集模式配置见[参数配置指南](参数配置指南.md)。

## 配置与正常输出

在首个 `[[datasource]]` 之前配置：

```toml
logLevel = "info"
scrapeSlowThresholdMs = 30000
```

未配置阈值时使用 30000ms；0 关闭 `scrape_diagnostic` 与 `sql_top`，独立错误、前台超时、panic、后台结束及轮次摘要继续按日志级别输出。负数、时长溢出或旧 `collectorSlowThresholdMs` 配置拒绝加载。配置文件模式下在文件中调整 `logLevel`；命令行模式沿用现有参数合并规则。

通过项目注册入口采集时，正常 INFO 每轮只有一条 `scrape_finished`：

```text
2026-11-13 10:07:19.499  INFO   采集完成 | 耗时 55ms | 采集任务 36 | SQL 55 | 样本 135 | 关联 S1
```

`runs` 是采集任务运行次数，包含不同数据源上的执行，不等于注册的采集器种类数。`samples` 是本轮转发的指标样本数，不等于指标名称数。0 SQL、0 样本照常显示，零样本本身不表示故障。

摘要总是 INFO，包括异常轮次；级别设为 WARN/ERROR 会过滤摘要。启动、数据源断连/恢复、独立错误和后台退出不计入正常轮次的一条限制。

启动监听保留完整指标地址，例如 `http://localhost:9200/metrics`。仅端口或通配监听地址生成本机 localhost 链接；明确指定的主机/IP 和自定义指标路径按配置生成。文件事件 `server_listening` 同时保留原 address、metric_path 与完整 url。

文件摘要核心字段为 `scrape_id/collection_duration_ms/runs/sql_calls/samples`。发生时追加 `skipped_runs/sql_unfinished_at_cutoff/sql_error_calls/dropped_samples/issue_runs/frontend_timeout_runs/unavailable_datasource_count`；这些可选计数省略表示零。异常任务和错误 SQL 的计数口径不同，不能相加。

## 失败怎么查看

```text
2026-11-13 10:07:19.470  ERROR  SQL执行失败 | 数据源 prod_primary_01 | 采集器 DbJobRunningInfo | 阶段 查询 | API耗时 25ms | 原因 "Error -2103: 第14 行附近出现错误:\n无效的模式名[SYSJOB]" | 关联 S1/R28/Q6
2026-11-13 10:07:19.470  ERROR  SQL详情 | 关联 S1/R28/Q6 | SQL "<原始 SQL 全文>"
2026-11-13 10:07:19.499  INFO   采集完成 | 耗时 55ms | 采集任务 36 | SQL 55 | 样本 135 | 异常任务 1 | SQL失败 1 | 关联 S1
```

示例 SQL 占位符在实际日志中是完整 SQL。错误、兼容探测和 Top 的 SQL 详情与主行同级，不会因为关闭 DEBUG 丢失 SQL。普通 SQL 错误不自动附堆栈，panic 显式保留完整栈。

SQL 包装层继续作为 SQL 错误的统一出口。`sql_error` 保存原始错误、SQL、数据源、采集器、run/query、首次错误阶段、实际耗时和启动时预算；错误工具保持原健康检查与降级动作。精确声明的兼容探测失败使用 DEBUG 的 `sql_probe_expected`，仅有 `purpose=probe` 不会把权限、网络、未知错误降级。

`error_stage_observed` 只在本次错误阶段与首次阶段不同时输出。重复错误仅首次观察时输出错误事件；完成记录在实际重复发生时附重复次数。

## 慢采集怎么定位

只有整轮耗时达到阈值且仍在采集时，本轮才输出一组 `scrape_diagnostic` 加最多五条 `sql_top`。SQL 错误、SQL 超时、前台超时、panic 不绕过整轮耗时门槛；提前发生的异常不会消耗后续时长触发机会。

```text
2026-11-13 10:07:49.444  INFO   采集耗时达到阈值 | 已耗时 30s | 阈值 30s | 未完成任务 2 | 活跃SQL 1 | 关联 S3/P1
2026-11-13 10:07:49.444  INFO   SQL耗时排名 #1 | 数据源 prod_primary_01 | 采集器 TableSpaceDateFileInfo | API耗时 28s | 总历时 30s | 状态 执行中 | 结果 待定 | 阶段 读取下一行 | 启动时剩余预算 35s | 关联 S3/R2/Q1/P1
2026-11-13 10:07:49.444  INFO   SQL详情 | 关联 S3/R2/Q1/P1 | SQL "<原始 SQL 全文>"
```

排名包含已成功、失败和仍执行的查询。`sql_duration_ms` 是进入 Query/Next/Scan/Err/Close/元数据等可观察 API 的累计耗时；`sql_wall_ms` 还包含两次 API 之间的业务处理和转发等待。两者都不是服务端纯执行时间，并发耗时不能相加作为整轮耗时。

`sql_phase=query/next/scan/err/close/columns/column_types/row_scan` 是当前 API；`between_calls` 表示调用之间。QueryRow.Scan 内部取行与关闭不可拆分，统一记为 row_scan。文件中的 `api_ms` 对象只含实际观测的阶段，省略的阶段表示未观测或不适用；0ms 可能是毫秒取整。

先看成功但很慢的查询，再看失败调用的 `budget_remaining_ms_at_start`。例如 A 成功用掉 29 秒，B 启动只剩 1 秒后超时，A 仍进入排名，B 的错误记录保留剩余预算。只能比较同一 run 实际共用的 context。多数采集器仍从全局首数据源读取 queryTimeout，慢 SQL 采集器使用注入的数据源配置，日志记录实际 context 的预算。

`sql_calls` 是应用进入数据库 API 的次数，包括进入时 context 已失效的尝试；database/sql 内部坏连接重试仍计一次。无 deadline 的预算为 null（控制台显示无限制），耗尽为 0。`context_state_at_start=deadline_exceeded/canceled` 时不能据此断言 SQL 已发送到数据库。

每轮始终输出最终摘要。阈值大于 0 且结束时已达到阈值，才允许附最终 Top：此前未输出诊断时由摘要充当总览；已有诊断时，候选、顺序、生命周期、结果或错误阶段改变才重打，单纯毫秒增长不刷新。

`snapshot_id` 指向最后已发布的快照。`top_emitted_count` 表示紧随本条总览/摘要实际输出的排名条数，省略表示本次没有输出排名。无 SQL 的慢轮次可以有快照编号而没有排名。文件每轮诊断 INFO 最多 12 条逻辑事件；控制台包含 Top 的 SQL 详情后最多 22 条展示记录。SQL 错误、前台超时、数据源状态及后台退出另计。

## 前台超时与后台结束

fast 模式在 run 上冻结前台 SQL 和计数，首次超时独立输出 WARN `collector_timeout`，即使尚未达到慢采集阈值也能看到：

```text
2026-11-13 10:07:24.444  WARN   采集前台超时 | 数据源 prod_primary_01 | 采集器 TableSpaceDateFileInfo | 前台预算 5s | 后台结束待确认 | 关联 S2/R2
```

前台超时不证明驱动取消成功。停止转发并确认后冻结样本计数；此后的 SQL、错误和结束记录带 `phase=background`，保留原轮次，不能改写已完成轮次或下一轮摘要。Top 的 `state=detached` 表示前台截止时 SQL 未结束。

`collector_background_finished` 表示后台函数已经退出。`background_duration_ms` 从 run 启动计算，控制台显示“启动后历时”，并非只计算转后台之后。后台开始的新 SQL 调用计入 `background_sql_calls`；前台开始、后台失败的 SQL 可能使后台失败数大于后台新调用数。

`active_stages` 仍反映 preflight/query/read_rows/process/metric_forward/error_handling/health_check/pool_close 等活动执行流。worker 与转发器分别记录，Ping 和连接池关闭时间不继续计入已返回的 SQL。

## DEBUG、读取与关联

DEBUG 记录 SQL 开始/完成、采集器开始/完成和阶段变化。开始记录不输出尚未产生的结果、行数和耗时。文件 `sql_started` 保留一次完整 SQL，`sql_finished` 不复制全文；普通控制台开始记录不展开 SQL。事后切换 DEBUG 无法补回未记录的成功 SQL 历史。

正常完成省略 `read_state=complete`，保留 `read_scope=first_row/first_result_set`；这只证明调用点声明的读取范围已完成，不代表消费了所有结果集。提前关闭为 partial，无法确定 QueryRow 扫描失败的范围时为 unconfirmed，行数可以是 null。null 与读到 0 行不同。首次 Scan 错误不被后续成功或 Close 覆盖，Rows 在显式 Close 后终结。

普通完成事件通过事件名表达生命周期，Top 快照仍保留独立的 `state/result/sql_phase`。正常 phase=collection 可以省略，后台必须显式标记。核心计数和已知零行仍输出，字段精简不是全局删除零值。

控制台 S/R/Q/P 分别是轮次、采集运行、SQL 和快照。短 S 号从现有完整 ID 派生，仅适用于单个进程阅读；跨进程检索使用文件完整 `scrape_id` 和时间。未知事件、未识别的新字段仍有兼容输出。

SQL、错误、堆栈中的控制字符使用可逆转义，每条展示记录一个物理行。同一事件主行和详情成组写出。文件是无颜色 JSON，保留毫秒、时区、caller；控制台 INFO/WARN/ERROR 摘要隐藏通用调用位置。SQL 不截断，绑定参数和结果集不进入诊断，SQL 字面量仍保留。

## 文件字段迁移

- `query_sequence` 删除，使用 `query_id`；正常状态和不适用的超时字段省略。
- `top_count/top_refreshed/last_top_snapshot_id` 替换为 `snapshot_id/top_emitted_count`。
- `query_ms/next_ms/scan_ms/err_ms/close_ms/columns_ms/column_types_ms/row_scan_ms` 变为 `api_ms` 对象。
- 普通摘要删除 `diagnostic_reasons/snapshot_at/active_stages/threshold_ms` 等诊断管理字段；慢诊断仍有 trigger、快照采样时间和活动阶段。
- 可选异常计数省略表示零，可选异常布尔省略表示 false；不能把这一约定用于行数未知或无 deadline。
- 程序采集日志应读取文件 JSON；原控制台 JSON 已改为中文文本。

## 验证范围

自动化测试覆盖模拟驱动、可控时钟、并发轮次、fast 后台归属、预算链、读取范围、编码、输出故障和字段迁移。opt-in `DIAGNOSTICS_EVIDENCE_DIR` 测试通过生产输出链路生成 normal/error/slow/debug/fast_background 的 `.console.txt` 与 `.file.jsonl`。

真实 DM 下的权限、慢查询、驱动取消及连接恢复仍需环境验证。中文格式化会增加控制台处理开销，文件变短不等于 CPU 一定减少；性能证据见[实施与审查记录](../plans/日志改造实施与审查记录.md)。
